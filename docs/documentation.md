# 项目文档规范

[English](documentation.en.md)

规范版本：1.0。适用于代码仓库及其关联的研究、产品、设计、工程、项目管理、发布和运营文档。

“必须”表示交付要求；“建议”表示默认实践，可按实际需要调整；“可”表示可选。目录和文件拆分按项目规模裁剪，强制交付要求不因规模减免。本项目按本规范执行；HarnessBrew 的迁移与检查见[专题入口](initiatives/process/documentation-standard/README.md)。

## 1. 基本原则

- 长期文档描述当前有效的知识、规则和操作方式；专题文档记录一次工作的需求、方案、执行和结果；发布记录描述一个版本的交付事实。
- 每项正式定义、任务状态和原始证据必须有一个维护位置，其他文档通过链接引用。概述必须与正式定义一致。
- 专题交付必须同步更新受影响的长期文档。历史过程保留当时背景，不能被误认为当前使用依据。
- 每份维护中文档必须有负责人；文档检查是交付门槛，定期复核是补充。

## 2. 目录结构

```text
README.md / README.en.md
CHANGELOG.md / CHANGELOG.en.md
docs/
├── README.md / README.en.md
├── documentation.md / documentation.en.md
├── research/
├── product/
├── design/
├── engineering/
│   └── decisions/
├── guides/
├── planning/
├── initiatives/
│   ├── feature/
│   ├── improvement/
│   ├── refactor/
│   ├── research/
│   └── process/
└── releases/
```

只创建有实际内容的目录。创建领域目录时必须提供双语 `README` 入口；其他子目录按导航需要增加入口。技术决策目录建立编号索引，专题目录必须有双语入口。

| 位置 | 职责与归属 |
| --- | --- |
| 根 README | 项目用途、核心能力、环境要求、最短可用示例、文档入口、许可证；详细使用说明链接 guides |
| 根 CHANGELOG | 按版本汇总新增、调整、修复和破坏性变化，链接详细发布记录；使用 current 状态 |
| docs/README | 文档地图及按读者需求组织的阅读路径 |
| research | 面向整个产品、可供多个专题复用的研究知识；注明时间、来源、方法局限和适用范围 |
| product | 当前有效的产品定位、用户群体、能力、业务规则和成功指标；具体变更需求放在专题 |
| design | 当前用户旅程、信息架构、交互模式、视觉规范和设计系统 |
| engineering | 当前架构、模块边界、数据模型、接口契约、安全和性能约束、技术决策 |
| guides | 可重复执行的使用、开发、测试、部署、运维、故障处理和发布操作说明 |
| planning | 跨专题路线图、优先级、里程碑、依赖、资源安排、整体风险和协作规则 |
| initiatives | 一项具体工作的目标到交付过程；专题相关研究材料和设计过程随专题存放 |
| releases | 按版本或明确发布事件记录内容、状态、兼容性、验收与发布证据 |

研究本身可建立专题；有长期复用价值的发现整理到 research，并链接原始材料。历史研究报告只证明对应时间、样本和问题下的发现。

## 3. 专题组织

围绕有明确目标和完成条件、需要关联多类信息或保留过程追溯的工作建立专题。专题可跨版本、包含多个阶段。小型修复、文案调整等可在 Issue/PR 中记录，并更新受影响文档。

| 分类 | 主要目标 |
| --- | --- |
| feature | 新增或扩展产品能力 |
| improvement | 改善已有能力的体验、性能或可靠性 |
| refactor | 改善内部结构和可维护性 |
| research | 专项调查、实验或探索 |
| process | 改进开发、协作、交付或运营流程 |

每个专题按主要目标选择一个分类，其他属性记录在入口中。目录使用稳定主题名，如 `initiatives/feature/adapter-upgrade/`，不按负责人、状态或实施阶段命名。

```text
initiatives/feature/adapter-upgrade/
├── README.md / README.en.md       必需：专题入口
├── requirements.md / .en.md      按需：需求和验收标准
├── research.md / .en.md          按需：研究问题、方法和发现
├── design.md / .en.md            按需：方案和决策
├── plan.md / .en.md              按需：执行任务、依赖、进度和风险
├── validation.md / .en.md        按需：验证和交付检查
├── assets/                      按需：图片、图表和附件
└── evidence/                    按需：报告、数据和产物摘要
```

小专题可全部合写在 README；复杂方案可拆成 `experience-design.md` 和 `technical-design.md`。专题计划管理具体执行，planning 管理跨专题安排。使用外部任务工具时，文档保留目标、里程碑及任务链接，任务状态以工具为准；否则在专题计划维护。必须声明唯一任务维护位置。

## 4. 状态与生命周期

| 文档类型 | 合法状态与含义 |
| --- | --- |
| 长期文档 | draft：草案；current：当前有效；superseded：已被替代或不再适用 |
| 专题 | proposed：评估中；active：推进中；paused：暂停；completed：达到完成条件；cancelled：终止 |
| 发布 | planned：计划中；verified：指定候选已验收；released：正式发布；cancelled：发布终止；withdrawn：已发布版本撤回 |

专题内拆分文件默认跟随专题状态，双语版本保持相同状态。专题中的历史内容由其上下文说明适用时间。导航文档和本规范使用长期文档状态。发布子文档跟随所属发布，原始材料和生成报告由入口管理。

专题暂停时必须记录原因和恢复条件；取消时记录原因与已有成果处理；完成时必须记录验收证据、遗留事项、中英文长期文档更新及独立评审。后续工作转入关联任务或专题。专题完成与正式发布分别记录。

归档通过状态和索引展示，保持路径稳定。当前导航优先展示 current 内容。superseded 文档必须在开头说明原因并链接替代文档；没有替代文档时明确说明。历史记录有事实错误时补充更正，后续行为变化记录在新专题和长期文档中。

verified 必须绑定候选产物身份和提交；产物变化后须重新验收。released 必须记录正式发布时间、产物身份、发布地址和证据；withdrawn 记录原因与后续建议。仓库版本号不能单独证明正式发布。

## 5. 命名、元信息与语言

目录和文件必须使用英文小写及连字符，入口固定为 `README.md`；`CHANGELOG.md` 为根目录约定例外。专题使用主题名，发布建议使用 `releases/1.3.0/`；重复发生的记录可使用日期，如 `interviews/2026-10-09-developer-a.md`。

所有正式维护的 Markdown 文档必须提供 YAML 元信息：

```yaml
---
title: Adapter 升级
status: active
owner: team-platform
updated: 2026-10-09
---
```

title 是文档标题；status 使用所属类型的合法值；owner 必须对应项目配置中可识别的人员或团队；updated 使用 `YYYY-MM-DD`，表示最后实质更新或有效性复核日期，纯格式修改不刷新。版本、适用范围、替代关系可增加字段或在正文记录。

默认中文为主语言，正式维护文档必须提供英文翻译；其他语言按需增加。中文使用标准文件名，英文使用 `.en.md`，其他语言使用约定的语言标识，如 `.ja.md`。对应版本互相链接，翻译注明中文主版本。英文 owner/status 与中文一致，title 翻译，updated 记录本语言实际更新或复核日期。

长期文档、专题入口与拆分文档、发布说明均执行双语要求。访谈原文、日志和机器生成报告保留原始语言，由双语入口或摘要说明。推进中翻译未同步时必须标注；交付前必须同步，不能用标注替代更新。

## 6. 模板与必要内容

统一必要内容，章节顺序和文件拆分可调整。不适用项必须说明原因；合写文档仍须覆盖适用内容。

| 类型 | 必需内容 |
| --- | --- |
| 长期文档 | 当前规则或事实、适用范围、相关引用 |
| 专题入口 | 目标、范围、状态、负责人、完成条件、相关文档导航 |
| 需求 | 用户问题、预期结果、范围与非目标、验收标准 |
| 研究 | 研究问题、方法与样本、发现、局限、来源 |
| 方案 | 背景与约束、方案、关键决策、风险、验证方式 |
| 计划 | 任务、依赖、负责人、进度、风险、完成条件 |
| 验证 | 验收结果、证据、遗留问题、交付文档检查、独立评审结论 |
| 发布 | 版本与状态、交付内容、兼容性、产物身份、验收与发布证据；未发生步骤明确标记 |
| 技术决策 | 背景、备选方案、决策与理由、后果、替代关系 |

有长期影响的技术选型、模块边界、格式或兼容策略必须记录在 `engineering/decisions/`，使用如 `0001-preparation-boundary.md` 的稳定编号，双语共享编号。草案为 draft，采纳且有效为 current；改变决策时新增记录，旧记录设为 superseded 并链接新记录。局部实现细节可留在专题方案。

## 7. 导航、引用、附件和证据

根 README 提供快速开始和总入口，docs/README 提供阅读路径，领域 README 说明范围并列出当前内容，initiatives/README 按分类和状态列专题，releases/README 按版本列状态。入口的标题和状态必须与源文档元信息一致，不能成为独立事实源；阅读顺序和用途说明由人工维护，可用工具生成或校验索引。

仓库内必须使用相对链接，必要时链接章节；中文优先链接中文，英文优先链接英文。无翻译的原始材料注明语言。文件移动时更新引用，链接检查必须验证文件和适用的章节锚点。历史证据注明对应版本或提交。

assets 保存理解内容所需的图片、图表和附件，evidence 保存验证报告、测量数据和产物摘要，均就近存放。专题证据归专题，版本级证据归发布，共享证据只保存一份。入口或验证文档必须解释用途、生成方式和对应提交/产物。大型或不适合入库的材料可放外部系统，记录可访问地址和必要身份信息。

## 8. 强制交付检查

文档检查是主要维护机制；未通过时不能合入变更、将专题标记 completed 或将发布标记 released。普通变更在 PR 记录，专题在 validation（合写时在 README）记录，发布引用对应检查结果，避免重复维护。

交付负责人必须显式评估 research、product、design、engineering、guides、planning、专题、发布、根入口/CHANGELOG 及证据的影响。每项记录“已更新”“经检查无需更新”或“不适用”，后两种必须说明原因。

### 8.1 统一检查记录

```text
交付对象：变更/专题/版本，PR，提交或工作区内容身份
负责人：
影响清单：领域/文档 | 处理结论 | 原因及中英文链接
自动检查：检查命令/CI | 结果 | 对应内容身份 | 日志
内容评审：实际行为、范围完整性、契约和恢复/兼容说明
双语核对：语义一致、示例和限制同步
示例验证：适用命令/示例、环境、结果；不适用时说明原因
验收证据：对应版本/提交/产物及链接
遗留问题：影响判断、后续任务和负责人
独立评审：身份、读取文件和证据、问题、修正与复核
最终结论：通过/未通过 | 评审者 | 日期 | 被评审内容身份
```

### 8.2 检查与评审责任

- 自动检查必须覆盖必填元信息、按文档类型的合法状态、命名、本地链接、双语配对和索引一致性，作为 CI 必过检查。
- 内容评审必须核对实际行为、完整影响范围、双语语义及适用示例的验证。文件存在不能证明翻译同步。
- 交付负责人完成更新并提交清单和证据；独立评审者不能是本次文档作者或修改者。
- 独立评审可由人类或独立 AI Agent 承担，使用同一清单。AI 必须独立读取相关实现、文档和证据，不能仅依赖作者摘要；记录身份、实际读取范围、提交、问题和复核结果。
- 检查与评审必须绑定具体提交；未提交草案可绑定基线提交及被审文件摘要，正式交付时须映射到交付提交。后续相关修改必须重新检查、评审受影响部分。

通过条件：影响清单完整，必过检查全部通过，中英文同步，没有本次交付必需但未完成的文档或证据问题。无关的既有问题可独立跟踪，必须说明不影响本次交付的依据；不能将翻译缺失或受影响旧文档不合规归为无关问题。

| 节点 | 强制确认 |
| --- | --- |
| 变更合入 | 本次影响评估、自动检查、内容与双语检查、独立评审 |
| 专题完成 | 目标验收、长期文档同步、双语更新、遗留事项和检查记录 |
| 正式发布 | 发布说明、兼容/升级指南、交付检查、候选与正式发布证据 |

检查可复用，但其提交、产物和范围必须适用于本次交付。负责人定期复核长期文档并更新 updated；超过项目期限标记“待复核”，不因日期自动改成 superseded。

## 9. 项目配置与迁移

每个项目必须在本文件中配置领域负责人、唯一任务管理位置、自动检查命令与 CI 门槛、独立评审和记录位置、复核周期、外部材料系统。配置必须使用已确认的实际值；未配置项明确标记，不得声称门槛已接入。

已有项目按以下顺序迁移：建立索引和文档清单；确认归属、状态、负责人并修正当前冲突；分批迁移路径、元信息和英文版本；接入自动检查；独立评审后完成迁移。

新变更立即执行完整交付要求，受影响旧文档同步补齐。其余缺口登记负责人及完成条件。迁移完成前不得声明全仓库符合规范。

### HarnessBrew 项目配置

| 配置 | 执行方式 |
| --- | --- |
| 规范状态 | 1.0，适用于本次及后续交付；迁移结果见专题验证 |
| 领域负责人 | project-maintainers：HarnessBrew 仓库维护者团队，负责已创建的各领域 |
| 任务管理 | 各专题 README 是该专题的唯一任务状态源；planning 只管理跨专题里程碑 |
| 自动检查 | npm run check:docs，包含在 npm run check；CI documentation job 执行 test:docs 和 check:docs |
| 独立评审 | 独立人类或 AI，结论与文件摘要写入专题验证/evidence；当前迁移记录为 independent-review.json |
| 复核周期 | current 文档每 90 天复核，交付检查优先；超期标记待复核，不自动失效 |
| 外部材料 | 仓库保存脱敏报告和摘要，大型候选包在忽略的 release-artifacts 或受保护 Actions artifacts |

维护中的根/docs 文档及源码和交付工具身份由独立评审记录绑定。相关文件改变后，默认 check:docs 拒绝旧结论；作者可用 `npm run check:docs -- --structure-only` 做准备检查，但它不能替代交付检查。新交付的独立结论由当前专题的验证记录链接，并更新全仓库检查所读取的批准记录（路径见检查脚本）。结构脚本不能自动证明语义正确或评审者独立性，独立评审必须实际执行。

CI 配置已写入仓库；GitHub 分支保护和 required status checks 属外部管理员设置，本次未操作，不能据本地配置声称远端保护已启用。正式合入仍须确保对应任务作为必过项。

以上配置是 HarnessBrew 的实际执行约定，推广时替换项目配置并保留强制要求。[迁移专题](initiatives/process/documentation-standard/README.md)记录清单、验证与遗留边界。
