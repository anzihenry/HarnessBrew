# 架构改进落地计划

状态：待实施。日期：2026-10-06。

基于当前 1.0.0 实现及架构评审制定。本文件描述拟议改动，不代表功能已经实现；当前行为以 [架构说明](../architecture.zh-CN.md) 为准。

## 1. 目标与交付顺序

优先解决慢来源长时间占用写锁，以及已有安装无法原子升级 Adapter 的问题；随后完善维护成本和 SDK 操作控制。保留单 npm 包、Git 来源、本地文件存储和现有提交点语义。

| 阶段 | 交付物 | 前置依赖 | 估算工程日 |
| --- | --- | --- | --- |
| P0 | 不变量、升级契约、可重复性能基准 | 无 | 2–3 |
| P1 | 用例与依赖边界整理 | P0 | 2–4 |
| P2 | 锁外准备、锁内复验 | P1 | 4–6 |
| P3a | 手动安装的 Adapter 原子升级 | P2、升级契约 | 4–6 |
| P3b | 受影响 Bundle 的联合升级 | P3a | 4–7 |
| P4 | 缓存及历史版本维护 | P2 的准备资源租约 | 4–6 |
| P5 | SDK 取消、进度及结构化结果 | P2，结果契约参考 P3 | 3–5 |

以上约 23–37 工程日，按一名熟悉仓库的开发者、含代码评审与专项测试估算；不是日历承诺，不包含等待真实 Codex 验收环境的时间。P0 完成后根据格式演进和基准结果修订。P4、P5 不阻塞 P3 的首轮交付。

建议三个发布批次：A = P0–P2；B = P3a–P3b；C = P4–P5。每批独立验证、独立决定版本号，不先承诺所有改动都能以 minor 发布。

逐项执行见 [批次任务拆分](architecture-improvement-tasks.zh-CN.md)：包含任务编号、前置依赖、文件范围、交付物和验收标准。本文负责设计约束与里程碑，任务清单负责完成状态。

## 2. 必须保持的不变量

1. 持久化的 committed Journal 仍是事务提交点；提交后清理失败不伪装成未提交。
2. 普通查询和预览遇到待恢复事务仍拒绝继续；doctor 可以输出不完整诊断。
3. 准备阶段只写可回收缓存，不修改活动 Home 状态、目标资源或 Bundle lock。
4. 执行前复验 Home 物理身份、revision、信任与能力、Adapter 摘要、来源、Manifest/lock 和目标指纹。
5. `apply(planId)` 不隐式重新规划；失效计划返回 `PLAN_STALE`。
6. 保留 Home → 用户级外部锁 → 排序目标锁的顺序。第一轮不移除外部总锁，不改变目录与子路径冲突保证。
7. 外部修改不因历史路径相同而被覆盖；共享文件保留无关键、区块和注释。
8. 修复和 Adapter 升级不隐式升级资产 commit，不提升来源信任或插件能力。
9. 未完成事务、有效计划及进行中的准备任务所引用的资源不能被 GC 删除。
10. 新插件的静态预览不执行插件代码；摘要用于身份与漂移检测，不宣称 JavaScript 插件受到沙箱保护。

## 3. P0：先固定契约与基准

涉及：`docs/design/`、`scripts/`、`tests/`，暂不改变业务行为。

- 将上述不变量映射到已有测试；补齐后续改造真正缺失的场景，不重复已有断言。
- 固定 Adapter 升级的状态转换、授权边界、Bundle lock 更新语义和错误码，形成独立 ADR。
- 盘点所有持久化格式与 SDK/CLI JSON 格式的严格解析规则。明确哪些新增字段需要 format version 升级，以及旧版本读取新数据时如何拒绝。
- 建立 10/100/1000 资产及小文件/较大文件两类确定性 fixture，测量 prepare、锁等待、锁持有、catalog 扫描、Journal 写入和总耗时。记录文件数量、字节数、系统与运行环境。
- 将阶段计时和 I/O 计数先做成内部可选 observer，避免提前锁定公共 API。报告不得包含目标文件正文、凭据或环境变量值。

验收：同一 fixture 可重复执行；有原始基准与运行命令；升级与兼容策略不再留有影响实现的开放决策。性能数字只作本机比较，不拿不同 CI 机器绝对耗时相互比较。

## 4. P1：用例与依赖边界整理

涉及：`src/application/service.ts`、`application/types.ts`、`diagnostics/doctor.ts`、`ports/`、事务相关模块。

- 从 `Application.build()` 提取来源、Adapter、安装/Bundle、维护用例。Application 保留公共入口、请求解析、生命周期和组合职责。
- 将诊断结果等共享契约放到其所属模块或独立契约文件；消除 diagnostics 对 application 的反向类型依赖。
- 为来源准备、计划缓存及必要执行 I/O 提供窄接口和默认 Node 实现；复用已有 StorageIO、GitClient、PlanningIO，不新建通用仓储框架。
- 协调器继续控制锁、提交和恢复顺序；提取具体内容准备/清理实现时，先保持相同调用次序和 Journal 格式。
- 增加导入边界检查：domain/resolution 不依赖 application、CLI 或可变外部 I/O；CLI 不绕过应用服务写入状态；diagnostics 不反向依赖应用编排。Node 的 path/crypto 等纯工具依赖单独允许。

验收：公共 API、CLI JSON、持久化格式不变；已有测试通过；禁止依赖能被检查脚本检出。拆分 PR 不夹带事务语义和性能优化。

## 5. P2：统一准备与提交流程

涉及：应用用例、`transactions/coordinator.ts`、`sources/manager.ts`、`application/cache.ts`、计划持久化。

拟议流程：读取受保护快照 → 释放锁 → 准备来源与计划 → 获取原有事务锁 → 按既有规则恢复 → 复验全部输入 → 执行与提交。

- 定义只含数据的 PreparedChange，保存 baseRevision、Home 身份、固定来源和 Adapter 身份、外部输入指纹、计划及准备资源引用。
- `plan()` 和 `execute()` 共用准备逻辑，`apply()` 读取保存的准备结果；三者共用执行前验证。
- 把 Git clone/fetch、可提前完成的内容 staging、插件副本准备移到事务外；插件输出和来源数据仍需在执行边界验证。
- 保留提交前必要的内容、目标和父目录检查，不以 mtime 缓存代替内容完整性验证。
- 准备结果因 revision 或授权变化失效时返回明确错误；第一版 `execute()` 也不自动重试整个准备过程。
- 首次 Home 初始化、执行前已有待恢复日志、两个服务同时准备等路径单独处理；初始化产生的新 revision 必须显式绑定，不能扩大忽略 revision 的例外。
- 为准备工作目录增加跨进程租约/引用登记。消费者先获得保护再读取缓存，释放后才允许维护任务回收；租约的锁顺序、崩溃清理与 GC 协议一起写入设计。

验收场景：

- 用可控闸门暂停 Git 准备时，同 Home 查询可完成，另一个 Home 对独立目标的写入可完成；不依赖易抖动的绝对耗时断言。
- 准备期间发生安装状态变更、撤销信任、插件漂移或目标修改时，执行拒绝且没有部分写入。
- 准备进程崩溃只留下可回收缓存；执行进程崩溃仍遵守现有恢复语义。
- 保存计划的执行不会因竞争静默改变原计划。
- 第一阶段发布不改变共享目标写入互斥保证。

## 6. P3：Adapter 原子升级

### 6.1 先解决授权与格式边界

现有协议已经分别具有 protocol、adapter version 和内容 signature，继续使用这些概念，不重复引入同义版本字段。内置 Adapter 签名当前由少数文件生成，需要定义完整的实现身份覆盖范围；是否包含依赖版本与构建产物由 P0 ADR 固定。

新插件只有运行 `plan()` 才能生成准确资源差异，因此不能同时承诺“完全静态”与“完整差异”。采用两步流程：

1. 静态检查候选包，返回候选摘要、声明、能力差异和受影响范围，不导入代码，不将结果冒充完整变更计划。
2. 调用方显式授权加载该候选摘要后，才能生成可执行升级计划；执行前再次核对摘要。普通 dry-run 不隐式提供此授权。CLI 与 SDK 表达方式在 P0 固定。

授权运行代码与提交安装变更分别表达。新版本所需额外能力必须明确授权；签名变化不会自动扩大能力。

### 6.2 P3a：仅手动安装

涉及：请求契约、Adapter registry、Planner、执行验证、状态发布、CLI。

- 新增拟议用例 `adapter.upgrade`，同一逻辑 Adapter 名称替换实现，不要求先移除已有 placement。
- 从已提交状态取得受影响资产及精确版本，只重新投放目标 Adapter 对应资源。
- Planner 比较旧 AppliedOperation 与新投放结果，生成更新或移除；不得借升级接管陌生资源。
- 将 Adapter 注册变更、目标文件变化及新的 operation fingerprints 放进同一个事务。不能先走 metadata publish 更新注册，再另起事务改文件。
- 升级失败保留旧注册和旧投放；若遇到无法安全回滚的外部修改，保留 Journal 并要求恢复。
- 任何活动 Bundle 使用该 Adapter 时，P3a 明确拒绝并列出 binding；不偷偷绕过其 lock 签名。

验收：内置及第三方 Adapter 均有升级测试；目标资源变化、共享文件保留、来源缓存缺失、能力变化、摘要漂移均有明确行为；资产 commit 不变；关键写入点 SIGKILL 后得到完整旧状态、完整新状态或明确的恢复冲突。

### 6.3 P3b：Bundle 联合升级

现有事务只携带一个 Bundle lock，且 binding 本身不足以自动找到所有 Manifest 文件。因此该阶段是独立交付，不把它视为一个布尔开关。

- 升级请求显式提供全部受影响 Bundle 的 Manifest 路径；按 manifest ID 与物理目录核对 binding，拒绝漏项、重复、缺失文件或不匹配声明。
- 保持锁定资产及依赖闭包不变，只按新 Adapter 更新必要签名和投放结果。若用户要同时升级资产，应另走资产/Bundle 更新用例。
- 将单个 bundleLock 扩展为明确的 lockfile 更新集合，包含每个文件的预条件、目标身份及内容。
- 注册、所有目标与所有受影响 lock 在同一事务内提交；扩展重叠资源检查、锁集合、Journal 验证及恢复测试。
- 不允许只更新本机注册而留下活动 Bundle 的旧签名；不自动修改请求范围之外的 checkout。
- 新格式需要版本升级时，提供显式、有预览和备份的迁移路径。未完成旧事务必须先用兼容版本恢复，再迁移；升级前的包及备份保留到验证完成。

验收：两个 Bundle 共享 Adapter、手动安装与 Bundle 混用、多 lock 竞争修改、Manifest 缺失和跨目录资源重叠均覆盖；在任一 lock 写入点崩溃不会被报告为部分成功。

## 7. P4：长期维护与垃圾回收

涉及：计划缓存、恢复暂存、来源/插件缓存、StateStore revisions、维护 CLI。

- 保留现有 cleanup 的内容库存语义，新增独立维护用例（名称拟为 maintenance/prune），支持预览、范围和保留策略。
- 建立引用集合：CURRENT、未完成 Journal、有效预览、准备租约、活动安装、选中的来源快照，以及必要的内容来源记录。
- 第一批只回收无引用且过期的 plans/restore 暂存；第二批支持来源/插件缓存；最后支持 revisions 保留数量/期限策略。
- 来源缓存目前仍是 catalog 查询和部分安装操作的输入，不能仅因“可重新下载”就删除。必须保留活动/选中引用，或先实现并验证按精确 commit 重建的路径。
- 历史 revisions 是审计快照，不承诺等同于可恢复备份。删除策略需说明剩余恢复能力。
- revisions 至少保护 CURRENT、未完成事务的 before/next revision，以及明确保留的审计版本。
- 采用标记、加锁复验、隔离、删除流程；进程崩溃后可继续。符号链接替换、未知文件与用户隔离副本均不自动删除。
- 用户修改产生的 quarantine 单独列出，由显式操作处置，不受普通 TTL 影响。

验收：预览与实际删除范围一致；并发准备/应用计划时引用不丢失；CURRENT 和恢复证据始终保留；中断删除可恢复；缓存维护后所承诺支持的查询/安装仍工作。

## 8. P5：SDK 操作控制与可诊断结果

涉及：`application/types.ts`、公共入口、Git/锁等待、CLI JSON。

- 拟增加独立于业务 request 的操作选项：signal、timeout、onProgress；不要将回调或 AbortSignal 序列化进计划。
- 取消向来源准备和锁等待传播。进入写事务后只在安全检查点响应；回滚/恢复本身不能被同一个已取消 signal 中断。
- committed 之后收到取消仍返回已提交结果；清理未完成明确标记，不能让调用方误判可以重试。
- `close()` 阻止新操作，并等待已启动操作结束；主动取消由各操作 signal 表达。明确重复 close 的行为。
- 使用判别联合表达预览变更；增加稳定的阶段事件和维护/恢复状态，逐步减少调用方解析 diagnostics 字符串的需要。
- 进度回调异常隔离，不得触发事务回滚；CLI JSON stdout 仍只输出一个最终文档，进度走 stderr。

验收：取消发生在 Git、锁等待、提交前、回滚中和提交后时均有确定结果；close 不释放尚在使用的资源；SDK 类型检查与 CLI JSON 契约测试通过。

## 10. 性能优化与发布退出条件

P0 基准与 P2 数据用于决定后续优化。暂不预设替换数据库、引入追加式 WAL 或移除全局锁。

- 若扫描主导耗时，先消除同一受保护操作内的重复解析/读取；共享文件按物理身份复用读取，仍保留必要时点的完整性检查。
- 若 Journal 写放大主导耗时，再独立设计 blob 引用或分段日志，并重做持久性与恢复证明；不与升级事务改造放在同一 PR。
- 发布 A 的关键指标：Git 准备等待不再占用 Home/外部写锁，现有恢复保证不下降。
- 发布 B 的关键指标：所有已支持的 Adapter 升级要么完整提交，要么保持旧状态/明确进入恢复；无静默资产升级或 Bundle 锁失配。
- 发布 C 的关键指标：可回收缓存有明确上界策略，活动引用和用户修改不误删，调用方能辨别取消与已经提交。

每批先完成候选包验证再更新当前架构说明。无持久化格式变化时可回退旧包；有格式变化时回退必须使用验证过的备份/迁移流程，不能只切换 npm 版本。关键不变量失败即阻止发布。

## 11. 第一轮执行入口

从 [A01：不变量与现有测试映射](architecture-improvement-tasks.zh-CN.md#a01) 开始，按任务前置依赖推进。任务状态只在拆分清单维护，避免与本计划重复记录。

下一轮开发从 PR 01 开始，以发布 A 作为第一个可独立验收的里程碑。
