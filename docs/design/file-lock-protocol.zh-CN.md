# 文件锁与进程崩溃恢复

## 协议

Home、Source 缓存和目标资源继续共享 `withFileLock`。锁目录是常驻命名空间，空目录不表示锁已占用。参与者使用 `<pid>-<uuid>.json`，每次调用创建新的 UUID，任何进程都不复用另一次调用的文件名。

采用 bakery 算法：

1. 在临时文件中写完参与记录，再通过原子 rename 发布 `ticket: null`，表示正在选号。
2. 扫描当前票号，选择最大值加一，再以同样方式原子发布票号。票号使用十进制大整数，避免整数溢出。
3. 等待扫描到的参与者完成选号，并等待 `(票号, UUID)` 排在自己之前的参与者退出。后来的参与者会看到自己的已发布票号，因此必须排在后面。
4. 执行动作，最终只移除自己唯一命名的记录和临时文件。命名空间目录永不被释放或回收流程删除。

这消除了 `mkdir` 和写入 owner 之间的无主锁窗口，也消除了回收锁 `.reclaim`。回收不会操作可能已属于后继持有者的公共路径。

## 崩溃与异常

- 发布记录之前崩溃：空目录和临时文件不占用锁。
- 选号或持锁时崩溃：其他参与者用 PID 存活检查识别死亡进程，忽略其票号并清理其唯一命名的文件。
- 释放期间崩溃：只涉及本次调用的文件，不影响后继参与者。
- 活进程、权限受限无法确认死亡的进程：始终保留，超时返回 `LOCK_TIMEOUT`，不按时间强行抢锁。
- 无法解释的已发布记录或非普通记录文件：返回 `LOCK_CORRUPT`，保留证据。部分写入只可能出现在尚未发布的 `.tmp` 文件。
- PID 被系统复用时采取保守行为，可能等待超时；不会据此夺取一个活进程的锁。

协议依赖本机文件系统的目录可见性和原子 rename，面向当前 macOS/Linux 单机进程协调。不能与旧版锁实现同时运行；旧版 `owner.json` 被明确报告为 `LOCK_CORRUPT`，停止旧进程后才能人工处理其遗留记录。旧版空目录和 `.reclaim` 遗留目录不占用新协议的锁。

`.store.lock` 常驻但空的目录是合法的 Home 内部元数据；不代表 Home 已初始化，也不使预览创建状态。

## 验证

真实子进程在目录创建、选号发布、票号暂存、票号发布、进入临界区、完成释放六个检查点被 SIGKILL，随后重新获取锁。另有五个进程同时选号并各执行八次更新，用独立的排他目录和计数器验证临界区不重叠、不丢更新。活进程选号、超时、异常释放、损坏记录，以及现有跨 Home 事务和崩溃恢复测试一并覆盖。
